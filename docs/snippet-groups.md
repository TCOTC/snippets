# 代码片段分组与折叠功能设计

> 状态：草案（供评审），对应 [TCOTC/snippets#20](https://github.com/TCOTC/snippets/issues/20)「代码片段支持分组」。
> 目标版本：snippets 2.x。本文只做设计，不涉及具体提交；工作区其余未提交改动与本设计无关。

## 1. 背景与目标

issue #20 提议为代码片段增加分组能力。核心痛点是片段数量多后菜单列表过长、查找困难（用户自述不习惯搜索，现用「注释分隔」手工分段，见 issue 附图）。诉求拆成五点：

1. 支持分组。
2. 分组支持展开 / 折叠。
3. 支持多层分组。
4. 设置可配：默认全部折叠或全部展开。
5. 拖动调整位置依然生效。

讨论过程中作者（TCOTC）反复强调一个硬约束：**片段数据是思源内核原生配置，每条记录只有 `id/name/content/type/enabled` 五个字段（外加 `disabledInPublish`），没有「分组」维度**，且要提防其他插件改写片段 ID 导致分组信息失配（曾考虑内容指纹 md5 方案后被否决，见第 11 节）。

本文结论先行：**采用插件自持「分组映射文件」保存归属与组序（不动内核记录结构），菜单渲染为一级可折叠分组树，底层片段顺序仍是现有单一有序数组（组内顺序由全局序推导），从而让第 5 点「拖拽排序依然生效」天然成立**。多级分组与「常用视图」等形态作为二期候选，不在本期。

## 2. 范围界定

### 2.1 范围内（v1）

- 分组映射：新建 / 重命名 / 删除组；组归属片段；删除组时组内片段并入「未分组」，不删除片段。
- 菜单渲染：分组折叠树（组头 + 组内片段），内置「未分组」兜底；CSS / JS 两个分区各自独立渲染组。
- 折叠交互：逐组折叠 / 展开，折叠状态本机记忆；设置项「默认状态：全部展开 / 全部折叠 / 记忆上次」。
- 拖拽：组内排序、跨组移动、拖到组头移入该组、拖到「未分组」移出组、悬停折叠组自动展开。
- 归属兜底：无归属的片段显示在「未分组」；映射引用但列表已不存在的 ID 被忽略并在打开菜单时一次性提示。
- 编辑与导入：新编辑对话框中同款列表视图复用分组渲染；新建 / 文件监听导入的片段一律进「未分组」，不从文件名推断归属。

### 2.2 明确不做（v1 之外，避免范围蔓延）

- 多层分组（issue 第 3 点）：弹出菜单落点命中区窄，树形拖拽误判率高，收益低，留二期评估。
- 「名称前缀自动分组」：不做隐式归属，仅可作为将来导出 / 分享的序列化格式，见第 3 节路线 C。
- 「自定义视图 / 常用集」（issue 讨论中作者引用的代码管理器形态）：按用途聚合而非层级收纳，二期结合分组再做。
- 内容指纹（md5）兜底：用户行为不可控、误判成本高、无必要，见第 11 节。
- 分组信息写回内核原生结构 / 原生 UI 展示（依赖上游改源码，见第 3 节路线 A，作为远期观察项，设计上保证可无损迁移）。

## 3. 前置路线与交互形态对比

### 3.1 数据层路线

| 路线 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A. 上游原生加字段 | 改思源 kernel，片段记录增加 group 字段 | 最干净，所有插件与原生 UI 可见 | 周期不可控；老数据要迁移；本仓库无法单方面推进 |
| B. 插件自持分组映射文件（推荐） | 插件 storage 下存 JSON：组树 + 组序 + 组内成员 ID 集合 | 立即可做；与「插件新增配置文件很正常」（issue 讨论）一致；结构可设计为日后无损迁移到路线 A | 仅本插件可见；ID 被其他插件改写会失配（用第 5.2 节兜底规则吸收） |
| C. 名称前缀虚拟分组 | 片段名用「组名/标题」约定，渲染时按前缀聚合 | 零持久化、零冲突、任何 UI 天然兼容 | 只能单层；组序由名称决定不能拖；空组无法表达；改名牵一发动全身 |

### 3.2 交互形态备选

| 形态 | 说明 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| 折叠分组树 | 组头行（折叠箭头 + 组名 + 计数），组内片段缩进，底部「未分组」 | 总览与收纳兼具；逐组折叠 + 默认态可配，完整覆盖 issue 五点诉求 | 需要扩展现有键盘导航与拖拽判定 | **推荐一期主方案** |
| 分组标签页 / 胶囊筛选 | 顶部一排 chips（全部 / 组一 / 组二…），点击只显示该组 | 单组聚焦清爽、切换成本低（issue 讨论中 su-dabiao 截图形态） | 与「总览 + 折叠」诉求不符；组多时 chips 横向溢出；日常逐项开关被「先选组」打断 | 可作折叠树的补充快速切换（可选），不做主形态 |
| 自定义视图（白名单） | 新建视图、勾选片段，顶部 tab 切换 | 适合「每天只动其中几个」 | 相当于在分组上再加配置层，一期成本高；不能替代折叠诉求 | 二期结合分组做 |
| 名称前缀 | 同路线 C 的视觉化 | 零实现 | 见路线 C | 仅作过渡 / 导出格式 |

### 3.3 推荐组合

**一期 = 折叠分组树**（菜单与编辑对话框共用同一渲染组件），落地 issue 五点；**二期**评估叠加「常用视图」；多级分组视需求单独立项。

## 4. 核心设计决策

| # | 决策 | 理由 |
|---|---|---|
| D1 | 分组信息存插件自有映射文件（组树 + 组序 + 组内成员 ID 集合），不改内核 conf.json 片段记录结构 | 原生记录无分组字段；映射文件方案已在 issue 讨论中收敛为可行；插件新增配置文件是正常行为 |
| D2 | 映射文件放插件 storage（`loadData` / `saveData`），不放 `data/snippets` | 避开本地文件监听（监听目录下 `.css` / `.js` 会被当片段导入，见第 9 节）；storage 写入可触发内核跨实例推送，天然获得同步通道 |
| D3 | **底层顺序仍是现有单一有序片段数组，组内顺序由全局序推导**；映射文件不另存「组内顺序」，只存成员 ID 集合（渲染时按全局序过滤） | 顺序唯一真相避免双写不一致；现有 `customSort` 拖拽「移动数组位置」逻辑整体复用，跨组移动只需挪位置 + 改归属，issue 第 5 点天然成立 |
| D4 | 无归属片段 →「未分组」；映射引用但列表不存在的 ID → 忽略并在打开菜单时一次性提示 | 防御其他插件改写 / 删除片段；只保证「不丢、不误伤」，不做内容指纹 |
| D5 | 数据分两层：**归属结构**（组 + 成员 + 组序，随插件 storage 跨窗口 / 跨设备同步）与**视图偏好**（逐组折叠状态，存 localStorage 仅本机） | 折叠是视图偏好，不必跨窗口强一致；归属是用户数据，必须一致；切分后冲突面最小 |
| D6 | 组绑定片段类型（组带 `type: "css" \| "js"`），CSS / JS 分区各自独立组空间 | 菜单现有 radio 分区按类型过滤，组随分区渲染，同名不同型互不干扰，交互最直观 |
| D7 | 搜索命中时忽略折叠状态，自动展开命中组 | 搜索是定位手段，折叠不应阻碍定位 |
| D8 | 组头不放启用开关，只放折叠箭头与计数；片段级开关、发布开关全部保留现状 | 避免与片段项 switch 语义混淆；发布逻辑（`disabledInPublish`）与分组正交，v1 不做发布态差异 |
| D9 | 分组功能与排序配置的关系：**组内顺序恒为用户自定义序**；`enabled` 类自动排序仅作用于「未分组」与组头排序，不重排组内成员 | 全局自动排序若作用到组内，会每次打开菜单打乱拖拽结果，与第 5 点直接冲突（详见第 7 节开放点） |

## 5. 数据与映射设计

### 5.1 归属结构文件（随插件 storage 同步）

新文件经 `saveData("plugin-groups.json", ...)` 落盘，与现有 `plugin-config.json`（配置，`STORAGE_NAME`）并列。JSON 结构草案：

```json
{
    "schemaVersion": 1,
    "groups": [
        {
            "id": "20260905120000-abcdefg",
            "type": "css",
            "name": "样式美化",
            "snippetIds": ["20250813161014-se1mend", "20250815083012-x2y3z4"]
        }
    ],
    "order": ["20260905120000-abcdefg"]
}
```

约定：

- `snippetIds` 仅为**成员集合**（渲染顺序不依赖数组内次序，由全局 `snippetsList` 数组序推导，见 D3）；删除片段时幂等摘除引用。
- `order` 表达组头显示顺序，空组也可保留并显示。
- `schemaVersion` 预留升级；文件损坏或解析失败时按空结构重建并弹一次提示，绝不阻断菜单打开。
- 结构文件不含任何折叠状态（D5）；不含片段代码原文（延续「广播 / 持久化不落代码原文」的既有约束——分组文件只含 ID 与元数据，代码仍在内核权威列表）。

### 5.2 一致性兜底规则

打开菜单（或任何一次列表重渲染）时执行一次轻量对账：

1. 列表中存在、但不在任何组 `snippetIds` 中的片段 → 归入内置「未分组」。
2. 组 `snippetIds` 引用了列表不存在的 ID → 忽略该项，并在本次菜单打开时一次性提示「有片段被其他行为修改，已移至未分组」（沿用 issue 讨论中「只保证不丢 + 提示」原则）。
3. 对账只读不改写文件；仅在用户主动做组操作或列表发生增删时顺带写回清理。

### 5.3 与现有排序方式的兼容

`sortSnippets`（`src/domain/snippet.ts`）现有 `fixedSort / customSort / enabledASC / enabledDESC / fileNameASC / fileNameDESC` 六种。分组视图下组内渲染顺序一律取全局数组序（即 `customSort` 语义的当前顺序），不受自动排序影响（D9）；自动排序若开启，只作用于「未分组」成员的排序与组头排序。具体联动文案与开关设计见第 7 节开放点。

## 6. 交互规格

### 6.1 菜单渲染层级

沿用现有 `SnippetsMenu` 结构（`.jcsm-top-container` 分区头部 + `.jcsm-snippets-container` 列表容器），把 `genMenuSnippetsItems` 输出的平铺片段项改为「组头 + 组内片段」分组输出：

- 组头行：折叠箭头（箭头随状态旋转）+ 组名 + 计数徽标（如 `12`）+ 尾部「⋯」操作（重命名 / 删除组 / 在此组新建片段）。
- 组内片段行：与现状完全一致的 `jcsm-snippet-item`（名称、编辑 / 复制 / 删除按钮、发布开关、启用开关），只是缩进一级。
- 内置「未分组」：结构与组头相同但固定显示在最后，不提供重命名 / 删除，可折叠。
- CSS / JS 分区过滤逻辑不变：按当前 `snippetsType` 过滤后，只渲染该类型的组与片段（D6）。

### 6.2 折叠与默认态

- 点击组头整行切换折叠，点击组名上的「⋯」弹出组操作（不冲突：箭头与 ⋯ 各自 `stopPropagation`）。
- 折叠状态写入 localStorage 键（如 `snippets.groupCollapsed.<type>.<groupId>`），打开菜单时按设置项取值：全部展开 / 全部折叠 / 记忆上次（读 localStorage；无记录时默认展开）。
- 折叠只隐藏组内片段 DOM（`fn__none` 同现有搜索过滤做法），不销毁，避免重渲染闪烁。

### 6.3 拖拽语义（`MenuDragSort` 扩展）

现有拖拽只支持「移到目标片段前 / 后」，分组后落点判定扩展为：

- 拖到组内片段间隙 → 组内排序（现有逻辑）。
- 拖到组头 → 移入该组（落到组内末尾）。
- 拖到「未分组」→ 移出组。
- 拖到已折叠组头并悬停 → 自动展开该组（标准树拖拽模式）。
- 跨组拖动实现：底层仍是「从全局数组移除 + 插到目标位置」一次 `SnippetStore.move`，同时更新目标片段在映射文件中的归属——**顺序移动与归属更新解耦**，归属更新不改变数组位置（位置由拖放点决定），避免双写不一致（D3）。

### 6.4 键盘导航

现有方向键遍历片段项需扩展为树遍历：组头可聚焦；`→` 展开折叠组，`←` 折叠已展开组并聚焦组头；跨组导航经过组头，不因折叠跳过整组内容之外的可达性（命中搜索时仍按现有关键字过滤规则处理）。

### 6.5 搜索协同

搜索命中时：忽略折叠态并展开命中组（D7），命中结果仍按组分段显示；关键字清空后恢复原折叠记忆态。CSS / JS 切换保留现有关键字与过滤状态的行为。

### 6.6 新建与空态

- 顶部「新建」按钮、组头「在此组新建片段」、以及「添加第一个 CSS / JS 片段」空态入口：新建对话框默认归属当前分区（选中组时归属该组，否则未分组），创建成功后按新归属渲染。
- 文件监听（`data/snippets`）与导入产生的片段一律进「未分组」，不从文件名推断（D4）。

## 7. 开放问题（进入实现前需拍板）

| # | 问题 | 候选方案 | 建议 |
|---|---|---|---|
| O1 | 自动排序（enabled / fileName 类）与「组内自定义序」如何共存 | a. 自动排序只作用于未分组与组头；b. 自动排序整体失效并提示切换到 customSort；c. 自动排序也重排组内（违背拖拽诉求） | a：组内保持拖拽序，未分组可自动排序，语义清晰 |
| O2 | 空组是否默认保留 | a. 保留（需显式组序）；b. 自动回收 | a：删除组是显式动作，空组应能存在（结构已支持 `order`） |
| O3 | 折叠状态跨窗口是否一致 | a. 本机 localStorage（D5）；b. 随 storage 同步 | a：视图偏好不强求一致，同步成本低 |
| O4 | 组操作广播：走插件 storage 跨实例推送（`onDataChanged`）还是扩展 `sync.ts` 广播协议 | 见第 8 节 | 归属结构变更低频 → 优先复用 storage 通道，不动广播协议（v1） |
| O5 | 分组功能的启用开关 | a. 设置项总开关，默认开；b. 无开关，片段一多自动分组 | a：显式可回退（分组文件存在即启用，清空即回到平铺） |

## 8. 跨窗口与跨设备同步

归属结构文件（第 5.1 节）经 `saveData` 落插件 storage（`data/storage/petal/<plugin-id>/`），思源内核已实现：任意实例写插件 storage 后向其余实例推送 `PushPluginStorageDataChanged`（发起实例自身排除）。本插件已覆盖 `onDataChanged` 做幂等热应用（既有 `plugin-config.json` 同款机制），因此：

- 本窗口：组操作后 `saveData` 写回 → 就地刷新菜单与对账。
- 其他窗口：收到 storage 变更 → 重新 `loadData` 归属结构 → 刷新菜单（与现有「跨窗口列表同步先自拉权威副本」模式一致）。
- 折叠状态（localStorage）不同步（D5 / O3）。

v1 不扩展 `sync.ts` 广播协议：归属结构变更频率远低于片段增删，storage 推送已够；若二期做「常用视图」等重 UI 状态再评估轻量广播。注意沿用既有约束：任何跨实例通道不得携带片段代码原文（本设计文件本身不含代码，天然合规）。

## 9. 现有架构集成点（代码事实）

| 模块 | 位置 | 与本功能的关系 |
|---|---|---|
| 片段模型 | `src/types.d.ts` `Snippet { id, name, content, type: "css"\|"js", enabled, disabledInPublish? }` | **不改**；分组是映射层叠加，片段记录结构保持内核原生 |
| 列表缓存与单一写路径 | `src/domain/snippet-store.ts` `SnippetStore`（`remove` / `upsert` / `insertBefore` / `move` / `replaceAll`，变更后通知菜单计数） | 拖拽 / 增删继续走它；`move` 保持 CSS 在前、JS 在后的分区边界落位，跨组移动复用它 |
| 排序纯函数 | `src/domain/snippet.ts` `sortSnippets` / `filterSnippetsByKeyword` / `snippetTitle` | 分组渲染过滤当前类型后按全局序输出；搜索过滤沿用 |
| 菜单渲染 | `src/ui/menu.ts`（`.jcsm-top-container` 顶部区 + `initSnippetsContainer` / `genMenuSnippetsItems` 输出 `.jcsm-snippet-item`，`data-type` / `data-id` 标识，radio 分区过滤） | 列表输出改为「组头 + 组内片段」；分区、计数、全局开关、搜索框均不动 |
| 拖拽 | `src/ui/menu-drag-sort.ts` `MenuDragSort`（桌面 mousedown + 移动端长按触摸、幽灵元素、边缘滚动、落点高亮、`isDragging` 防误点） | 落点判定扩展组头 / 未分组 / 悬停展开；点按折叠与拖拽判定需互斥（组头可拖移入、点按折叠） |
| 编辑器 | `src/ui/snippets-dialog.ts` + `src/ui/codemirror.ts` + `src/ui/editor-manager.ts` | 编辑保存不涉及归属（归属只随菜单操作变更）；若对话框内置列表则复用分组渲染组件 |
| 配置 | `src/config/config-service.ts`（`STORAGE_NAME = "plugin-config.json"`、`createSnippetsConfigItems`、`saveData` 写回内核响应判定） | 新增「默认折叠状态」valueItem 走既有热应用；分组文件用独立 storage 键，**不进** valueItem 收集路径（避免被 `persistConfig` 覆盖，与 gist-sync 的 D4 同款约束） |
| 文件监听 | `src/services/file-watch.ts`（监听 `data/snippets` 下 `.css` / `.js`） | 分组文件不落此目录（D2）；监听加载的片段进未分组 |
| i18n | `src/i18n/{en,ja,zh-CN,zh-TW}.json`（2 空格缩进） | 新增键四语言同步：组名默认值、组操作、默认折叠态选项、孤儿提示等 |

## 11. 风险与已否决方案备忘

- **内容指纹（md5）兜底（已否决）**：issue 讨论中曾提出「id + 根据类型 / 描述 / 代码计算的 md5」判定同片段，避免其他插件改 ID 后失配。否决理由与讨论一致：用户行为不可控、同名片段误判、防御成本高于实际收益；按 D4 的「归未分组 + 提示一次」已覆盖核心诉求（不丢片段）。
- **名称前缀自动分组（否决为主方案）**：见路线 C 缺点；若用户习惯已用「注释分隔」，可提供一次性「按注释 / 前缀导入为分组」的迁移助手作为可选增强，不做常驻逻辑。
- **多级分组（延期）**：菜单垂直空间与拖拽落点命中率不支持可靠树拖拽；一级分组 + 未分组已覆盖 issue 截图所示实际用法。
- **其他插件直接改片段顺序**：`conf.json` 顺序被外部改写时，分组文件按 ID 匹配仍能正确聚组，只是组内相对顺序随全局序变化；如需固定组内顺序再引入「组内显式序」字段（D3 的备选升级路径）。
- **菜单性能**：折叠用 `fn__none` 隐藏而非移除 DOM，片段极多（数百）时组头行轻量、单次渲染可控；若实测卡顿再改懒渲染。
